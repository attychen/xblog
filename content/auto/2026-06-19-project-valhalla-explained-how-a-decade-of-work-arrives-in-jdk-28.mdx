## 1. 引言：这一切究竟关乎什么？

Valhalla项目自始至终的口号是：“编码如类，运行如int”（codes like a class, works like an int）。这一句话就概括了整个项目的要点：我们希望编写正常、可读的类，包含方法、构造函数验证和合理的字段名，但同时希望JVM能够像处理基本类型（primitives）一样高效地处理它们。

要理解为什么这是一个问题，必须回溯到Java的基础。在Java中，除了八种基本类型（int、long、double、boolean等）之外，一切都是引用类型（reference type）。当你编写`Point p = new Point(1, 2)`时，变量`p`并不是一个点。变量`p`是一个指针，一张衣帽间的存根：堆上的某个地方有一个对象，而你手里拿着一张写有它地址的纸条。每次你想读取一个字段，JVM都必须“去衣帽间”，通过指针进行一次跳转（指针间接引用，pointer indirection）。对于单个对象来说，这不算什么。问题在于规模。

堆上的每个对象都有自己的头部（header，大约十几个字节的元数据：用于让JVM知道它是什么类型，以及是否有人在对其进行同步等）。顺便提一句，这正是Project Lilliput最近一直在解决的问题，帮助缩小对象头部的大小。但头部大小并非全部。每个对象都必须被分配（allocate），之后还要被垃圾回收（garbage collected）。而且，由于对象分散在堆上，一个包含一百万个Point的数组，实际上就是一百万张纸条，指向散落在整个仓库里的一百万个盒子。Brian Goetz在他的“State of Valhalla”文档中，将这种内存布局称为“蓬松的”（fluffy）：膨胀、臃肿。

我们梦想的是一种紧凑的布局（dense layout），数据并排存放。为什么紧凑性如此重要？因为硬件的变化速度超过了Java。1995年，一次内存访问的成本大致相当于一次CPU操作。如今，CPU的速度比主内存快两个数量级，整个差距由缓存（cache）来弥合。处理器以称为缓存行（cache line，通常为64字节）的块来读取内存。如果数据紧凑且有序，一次读取就能同时带来大量有用的值。如果我们通过指针跳转，每次访问都有缓存未命中（cache miss）的风险，其速度可能比命中慢一百倍。这就是引用局部性（locality of reference），也是整场游戏真正的赌注。

“但是JVM有逃逸分析（escape analysis）”，敏锐的人会这样说。没错：虚拟机可以识别出某个对象从未“逃逸”出代码的局部片段，那么它根本就不会分配该对象。从程序员的角度看，对象似乎存在，但实际上它的字段被分散到普通变量或CPU寄存器中。在最好的情况下，分配和后续垃圾回收的开销几乎降为零。问题在于，这种优化是不可预测且脆弱的。它只在JIT编译器能够高置信度地追踪对象的整个流程时才有效。但只要对象落入另一个类的字段、被存入数组、被传入更复杂的方法、或者出现在JIT能分析的代码边界之外，整个技巧就会失效。源代码保持不变，但性能行为可能发生巨大变化。

这正是经验丰富的JVM程序员将逃逸分析视为一个不错的额外奖励，而非项目基础的原因。如果应用程序的性能取决于某个特定JIT版本是否能够应用这种优化，那么很容易陷入难以预测的性能回退陷阱。一次小的重构、一次JDK更新、或代码结构的改变，都可能将对象送回堆上，分配和垃圾回收的开销将全面恢复。

这就只剩下一种蛮力选项：放弃对象，手动编码数据。不使用Color类，而是持有三个字节r, g, b。这不仅仅是一个学术例子。这种方法在游戏引擎、图形库、图像处理系统、数据库、分析引擎和HPC代码中已经使用了多年，在这些场景中，每一个字节的内存和每一次分配都至关重要。问题在于，速度是以安全性和可读性为代价的。我们失去了名称、私有状态、验证和方法。JEP 401给出了一个简单的例子：一个处理“原始”颜色字节的开发人员可能会错误地将它们解释为BGR而不是RGB，交换红色和蓝色，从而悄无声息地破坏整个图像。一个类不会允许这种情况发生。一个裸的int呢？当然可以。正是这种两难境地——要么是方便的类，要么是快速的基本类型——正是Valhalla试图消除的。

## 2. 开端：2014年，“六个博士”，以及五个原型

官方上，Project Valhalla始于2014年。James Gosling当时将其描述为“六个博士打成一个结”，这绝非夸张。有趣的是，这个想法比项目本身更古老：Java的创造者早在该语言的第一版就想要值类型（value types），但在1995年他们放弃了，因为问题太难了。

目标设定得雄心勃勃：恢复编程模型与现代硬件性能特性之间的一致性。换句话说，让程序员能够声明自己的类型，这些类型在内存中像基本类型一样扁平紧凑，但外观和行为像普通类。说起来容易做起来难。

在接下来的几年里，团队构建了五个不同的原型，每个原型都探索了问题的不同方面。而这是故事中最有趣的部分开始的地方，因为要理解Valhalla当前的形式，你必须看到有多少想法在途中被抛弃了。

早期的原型走向了我们现在称为“Q World”的方向。它假设新的值类型是与对象根本不同的东西，拥有独立的类型描述符（type descriptors）、独立的字节码（bytecodes）和独立的顶层类型（top types），就像基本类型一样。听起来很合理：如果它们应该像int一样工作，就让它们像int一样表示。问题在于，这种分离用额外的复杂性淹没了整个JVM类型系统：所有事情都必须做两个版本。

突破来自于一个名为“L World”的原型（大约在2019年）。这个名字源于值类型开始与对象引用共享相同的“L载体”（L描述符，与JVM用于普通引用的相同）。团队原本期望这种统一太难实现，然而，令他们自己惊讶的是，它竟然在没有重大妥协的情况下成功了，并且顺便解决了早期轮次中的一大堆问题。

L World还产生了一个更根本的“顿悟”，塑造了之后的一切：语言模型和JVM模型不必百分之百重叠。L World是虚拟机的正确模型，但你可以将其视为一个翻译目标，并在语言中为程序员提供更方便的东西。这种层的分离被证明是项目其余部分的关键。

也正是在那时，将工作分为两个阶段的计划变得明确：首先是值类（当时还叫别的名字，稍后会提到），然后才是特化泛型（specialized generics）。我们将在第6节回到泛型，因为那是一个独立的、更长的论述。

## 3. 思想的演变：命名的过山车

如果你曾经尝试阅读关于Valhalla的资料，却被一堆矛盾的术语搞得一头雾水，那不是你的错。这里的命名改变了好几次，而且不是表面上的改变：每个名称变化的背后都是模型的变化。让我们追溯一下，因为这是展示这个特性是如何被设计出来的最佳例证。

阶段1：值类型（value types）：最早的术语。很模糊，因为当时还不清楚这些东西到底是什么。

阶段2：内联类（inline classes）：大约在2019-2020年，一个区别被确定下来，其本质延续至今：类被分为恒等类（identity classes，具有恒等性的类，也就是我们迄今为止所知道的一切）和新的内联类（没有恒等性）。那时提出了“编码如类，运行如int”的口号，并设定了基本约束：内联类默认是final的，它们的字段是final的，你不能对它们进行同步。

阶段3：“基本类型类”（primitive classes）和双投影模型（two-projection model）。这里变得有趣了，因为这正是那个被大幅削减的想法。在2021年的“State of Valhalla”文档中，Valhalla承诺了三件事：值对象（value objects）、基本类型类（primitive classes）和特化泛型（specialized generics）。“基本类型类”的想法是，一个单一类型将有两个投影：一个值变体（value variant，扁平，永不为null，行为类似基本类型）和一个引用变体（reference variant，一个允许null的包装盒）。在不同的迭代中，这被写作`Point.val/Point.ref`，后来他们尝试了`Point!`和`Point?`的语法。

这个模型很强大，但在心智上也很沉重。程序员每天都要在同一类型的两种形式之间周旋，并理解它们之间的转换何时发生。团队秉承“为用户简化模型，即使以牺牲性能上限为代价”的信条，最终拆除了这种二元论。

阶段4（今天）：“值类”（value classes）和“值对象”（value objects）。当前的JEP 401，由Dan Smith撰写（审阅者：Brian Goetz），将其简单化。有一件新事物：一个值类，用`value`修饰符声明。它的实例是值对象：没有恒等性的对象。并且（这是关键）值类仍然是一个引用类型。整个关于非空性（non-nullability）的棘手问题已被分离到一个单独的、可选的JEP（空限制值类类型，Null-Restricted Value Class Types）中，我们稍后会提到。

因此，我们用一个复杂的概念换来了两个简单、正交的概念：“它有恒等性吗？”以及，稍后单独处理，“它允许null吗？”值得记住，因为如果你遇到一篇较旧的文章（或者Baeldung将“基本类型类”描述为一个独立的机制），你读到的是一个过时的模型。在OpenJDK的规范中，那个意义上的“基本类型类”已不复存在。

沿途还有更多东西被抛弃了。最初的“值对象”JEP草案被撤回，并被JEP 401取代。最初的“通用泛型”（Universal Generics）草案也回去返工了。JEP 401伴随着JEP 402：增强的基本类型装箱（Enhanced Primitive Boxing，也是预览版），以及一整个系列的早期访问构建版本（LW1, LW2, LW3...）和来自JVM语言峰会（JVM Language Summit）的演讲，其中包括Frédéric Parain关于堆扁平化（heap flattening）和Daniel Smith关于新对象初始化模型的演讲。

本节的寓意是：十二年不是十二年的“编写代码”。那是十二年的拒绝想法，直到留下那个真正可以维护的想法。

## 4. Valhalla今天如何工作：JDK 28中的值类模型

让我们进入具体细节。以下是我们确切得到的东西。

声明。你通过添加`value`修饰符来创建一个值类：
```java
value class USDCurrency implements Comparable&lt;USDCurrency&gt; &#123;
    private int cents; // 隐式final

    public USDCurrency(int dollars, int cents) &#123;
        this.cents = dollars * 100 + cents;
    &#125;

    public USDCurrency plus(USDCurrency that) &#123;
        return new USDCurrency(0, this.cents + that.cents);
    &#125;

    // dollars(), cents(), compareTo(), toString()...
&#125;
```
它也可以是一个值记录（value record）。规则是：所有实例字段都是隐式final的，方法不能是`synchronized`，类默认是final的（或者它可以形成一个由值类和抽象值类组成的层次结构），它不能继承自具有恒等性的类，但可以愉快地实现接口。除了这些约束，它是一个普通的类。

定义性特征：没有恒等性。这是核心。一个普通对象具有恒等性：两个分别创建的`new Point(1,2)`是两个不同的对象，即使它们的内容完全相同。一个值对象没有恒等性，就像不存在两个“不同的”int类型的4一样。由此衍生出所有后果：

`==`改变了含义。直到现在，`==`比较的是恒等性（是否是同一个地址）。对于值对象，`==`检查可替换性（substitutability）：两个值是否是同一个类，并且具有相同的字段，递归比较（基本类型字段逐位比较，对象字段再次通过`==`比较）。这就是为什么`new USDCurrency(3,95) == new USDCurrency(3,95)`返回`true`。这是个好消息：它终结了与`Integer`上`==`的著名混淆。但要注意：`==`查看的是内部状态，这并不总是对象所代表的东西，所以对于“这是相同的数据吗”的比较，继续使用`equals`。

`synchronized`抛出异常。没有东西可以同步。尝试会导致`IdentityException`。当你需要强制恒等性时，你有新的辅助方法`Objects.requireIdentity`和`Objects.hasIdentity`。

现在是最重要的概念陷阱：值对象仍然可以为null。这令所有认为“值 = 像基本类型 = 永不为null”的人感到惊讶。在JDK 28模型中，值类是一个引用类型，所以`USDCurrency d = null;`是完全合法的。非空类型（带有空限制）是一个单独的、未来的JEP。它们不在JDK 28中。我们会回到这一点，因为这不是一个细节：它是实现完整性能的关键。

它在内存中如何存放

JEP 401赋予了JVM自由，使得值对象可以通过两种主要方式进行优化。

标量化（Scalarization）是一种JIT编译器技术。对一个值对象的引用被“分解为其质因数”，还原为其本质，即字段集合，没有包装。JIT不是传递指向Color的指针，而是简单地传递三个字节r, g, b（加上一个指示引用是否为null的标志位）。这样的对象实际上是免费的：没有分配，没有GC工作。这有点像逃逸分析，但可预测性更强，范围更广：即使跨越JIT未内联的方法调用边界，它也能工作。限制是：当一个变量的类型是值类的超类型（例如Object，或者重要的是，一个被擦除的泛型参数）时，标量化通常不起作用。此时，对象必须在堆上物化（materialized）。

堆扁平化（Heap flattening）是第二种机制。对象的本质被编码成一个紧凑的位向量，并直接写入字段或数组单元，而不需要指向内存中另一个位置的指针。这正是密度和局部性产生的地方。不过，这里有一个值得注意的陷阱：扁平化的数据必须能够原子性地读写（否则在并发访问下存在“撕裂”（tearing）风险）。在典型平台上，“足够小”目前意味着最多64位，包括null标志。这就是为什么许多小的值类会很好地扁平化，但一个包含两个int字段或一个double的类可能无法适应原子写入，最终仍然作为普通对象存在于堆上。未来，128位编码将会到来，而前面提到的关于空限制类型的JEP将允许通过放弃原子性保证来扁平化更大的类。这正是非空性不再是表面功夫，而成为性能杠杆的时刻。

以新视角看待装箱与拆箱

还记得古老的装箱（boxing）成本吗？将int包装在Integer中？在新模型中，包装类本身变成了值类（当预览开启时，Integer、Long、Double等失去了它们的恒等性）。由于包装盒不再具有恒等性，JVM可以将其标量化和扁平化。效果是：`Integer[]`开始接近`int[]`的效率，而装箱开销，引用JEP 401的话，急剧减少。伴随的JEP 402（增强的基本类型装箱）更进一步，平滑了基本类型与其包装盒之间的转换，为编写像`List&lt;int&gt;`这样的东西开辟了道路。但这是一个独立的、仍在成熟的部分，所以不要假设它会与401一起完整推出。

数组

这是效果最明显的地方。`Color[]`数组不再持有指向一百万个分散对象的一百万个指针，而是可以直接存储扁平化的、32位编码的连续颜色（再次强调：加上一个null标志）。从内存角度看，这样的数组开始看起来并表现得像一个普通的`int[]`：一个连续的数据块，处理器逐缓存行顺序扫描。

为了使这一切成为可能，一些非常深层次的基础被改变了：新的`value`修饰符；严格的构造规则（在任何人看到新对象之前，实际上是在`super()`调用之前，所有字段都必须被设置，这样对final字段的“修改”就永远不会被观察到）；将`==`重新定义为可替换性测试；向引用比较字节码（acmp）添加值对象检查；标量化和扁平化机制；`IdentityException`；以及现有“基于值”（value-based）类的迁移。简而言之，这不是语法糖。这是对自1995年以来在Java中一直成立的一个假设的重建：每个对象都有恒等性。

## 5. 一个实际例子：逐步对比前后变化

让我们采用最简单的情况，并对其进行追踪，以便即使不了解JVM内部原理也能清楚理解。

Valhalla之前：
```java
final class Point &#123; // 一个具有恒等性的普通类
    final int x;
    final int y;
    Point(int x, int y) &#123;
        this.x = x;
        this.y = y;
    &#125;
&#125;

Point[] points = new Point[1_000_000];
```
这里在内存中发生了什么？`points`数组是一百万个指针。每个指针指向堆上某处的一个单独的`Point`对象。而每个这样的对象不仅仅是它的两个int（8字节），还有一个头部（另外十几个字节的元数据）。这些对象是分散的：分配器在不同的时间、不同的位置创建了它们。当你遍历数组并求和坐标时，对于每个点，处理器必须：从数组中读取指针，跳转到指定的地址（有缓存未命中的风险），读取字段。重复一百万次。这正是第1节中那个“蓬松的”布局。

Valhalla之后：
```java
value class Point &#123; // 一个没有恒等性的值类
    final int x;
    final int y;
    Point(int x, int y) &#123;
        this.x = x;
        this.y = y;
    &#125;
&#125;

Point[] points = new Point[1_000_000];
```
代码中的区别只有一个词：`value`。但内存中的区别是根本性的。JVM现在可以将值本身存储在数组中，一个接一个地紧凑排列：每个点8个字节（加上一个可能的null标志位，但为了这个例子，我们假设它被优化掉了）。没有头部，没有指针，没有间接引用。遍历这个数组时，处理器以流式方式读取连续的内存块。缓存未命中率骤降。

这不仅仅是内存节省。这是对内存墙（memory wall）的绕过。

当然，并非所有值类都会变得如此之小。一个包含`double`和`int`的类可能无法原子性地适应64位，并且可能无法完全扁平化。但即使如此，JVM也可以应用标量化，将字段分配到寄存器中，避免分配。关键在于，这种优化现在是可预测的，并且由语言模型保证，而不是依赖于JIT是否能够追踪到逃逸路径。

## 6. 特化泛型：缺失的部分

Valhalla的完整愿景包括特化泛型（specialized generics），通常被称为“通用泛型”（Universal Generics）。这个想法是让泛型能够与基本类型和值类一起工作，而不仅仅是引用类型。目前，`ArrayList&lt;Integer&gt;`在内部使用`Object[]`，并依赖于装箱。有了特化泛型，`ArrayList&lt;int&gt;`或`ArrayList&lt;Point&gt;`（其中Point是一个值类）将能够直接存储扁平化的值，无需装箱或间接引用。

然而，特化泛型不在JDK 28中。它被推迟到未来的JEP中。原因很简单：它非常困难。泛型在Java中是通过类型擦除（type erasure）实现的，这意味着在运行时，`List&lt;String&gt;`和`List&lt;Integer&gt;`都是同一个类`List`。要使泛型能够处理值类型，需要一种方式在运行时表示不同的特化版本，同时保持与现有代码的向后兼容性。

团队已经探索了多种方法，包括“模板化”泛型（templatized generics），其中编译器为每个使用的类型参数组合生成特化版本，以及“值感知”泛型（value-aware generics），其中JVM在运行时处理特化。目前，共识似乎是朝着一种混合方法发展，但细节仍在制定中。

这意味着，虽然值类本身在JDK 28中可用，但它们的全部潜力——与泛型集合的无缝集成——尚未实现。在此期间，你可以使用值类，但如果你需要将它们存储在集合中，你可能会遇到装箱或间接引用的开销，这取决于具体情况。团队明确表示，特化泛型是Valhalla的第二阶段，并且正在积极工作中。

## 7. 这对Java开发者意味着什么？

值类的引入是Java语言和JVM的一次深刻变革。它解决了Java中一个长期存在的痛点：不得不在方便的对象和高效的基本类型之间做出选择。以下是关键要点：

1. **性能提升**：对于数据密集型应用程序，值类可以显著减少内存占用和垃圾回收压力，同时通过更好的引用局部性提高缓存效率。这对于游戏、图形、科学计算、金融建模和任何处理大量小对象的领域尤其重要。

2. **更清晰的语义**：`==`现在对值对象进行结构比较，消除了与包装器类型（如`Integer`）相关的常见陷阱。然而，开发者需要理解`==`和`equals`之间的区别，因为`==`比较的是字段值，而`equals`可能实现自定义逻辑。

3. **新的设计模式**：值类鼓励创建小的、不可变的、无恒等性的类型，这些类型可以像基本类型一样被自由复制和传递。这可能导致更函数式的编程风格，并减少对防御性拷贝（defensive copies）的需求。

4. **迁移路径**：现有的“基于值”的类（如`java.time.LocalDate`和`Optional`）将逐步迁移为值类。这应该对大多数开发者是透明的，但依赖于恒等性（例如，使用`==`比较或同步）的代码可能需要更新。

5. **预览状态**：在JDK 28中，值类是一个预览特性，默认禁用。这意味着它可能在未来版本中发生变化。开发者可以通过在编译和运行时启用预览标志来尝试它，但不建议在生产环境中使用，直到它成为稳定特性。

6. **学习曲线**：虽然值类的概念很简单，但理解其含义——特别是关于null、恒等性和性能的微妙之处——需要一些学习。开发者需要熟悉JEP 401中概述的约束和最佳实践。

总的来说，Valhalla代表了Java性能工具箱中的一个强大新工具。它不是万能药，但对于正确的问题，它可以带来数量级的改进。随着特化泛型的到来，其影响将更加深远。

## 8. 结论：一个时代的终结，一个新时代的开始

Project Valhalla进入JDK 28标志着Java历史上一个漫长而曲折的篇章的结束。从2014年的最初概念，到五个原型，再到无数次命名变更和模型简化，值类的最终形式是多年深思熟虑的设计和工程努力的结晶。

Brian Goetz的评论——“他们永远不会发布它”的人群现在将平滑地转向“但他们没有发布最重要的部分”——恰如其分地捕捉了社区的情绪。Valhalla的完整愿景，包括特化泛型，尚未实现。但基础已经奠定。值类本身就是一个强大的特性，它改变了Java中数据建模和性能优化的格局。

对于JVM生态系统来说，这是一个激动人心的时刻。Valhalla，连同Project Lilliput（更小的对象头）、Project Panama（外部函数与内存API）和Project Loom（虚拟线程），正在将Java转变为一个更适合现代硬件和现代应用程序需求的语言。

所以，泡杯咖啡，下载JDK 28的早期访问版本，开始尝试值类吧。它们可能不会立即改变你编写所有代码的方式，但它们为你提供了一个新的工具，用于构建更高效、更可预测和更安全的系统。Valhalla的大门已经打开。是时候探索了。
