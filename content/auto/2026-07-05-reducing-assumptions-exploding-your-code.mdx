## 1. 优雅的脚本

我们都写过这样的脚本：它们完美地组合在一起，可读性强，但只假设了顺利路径。世界可以是快乐的，但它也充满缺陷和不完美。为了让你的代码在这样的世界中运行，甚至增加价值，它必须处理这些不完美。

## 2. 我们现实世界的例子

我们的脚本将接受一个ID作为参数。它会在setup.json中查找API令牌（API token），并向远程服务器发起请求下载一个PDF。下载文件的名称由服务器决定。这很简单，但有点现实中的混乱——但嘿，我们是程序员，这就是我们做的，我们擅长的，对吧 :) 对吧 :I（想到了所有vibeco）

## 3. Python版本

Python是编程的通用语言。开始吧！

import sys, json, requests, re
from requests.auth import HTTPBasicAuth

id = int(sys.argv[1])

with open('setup.json') as f:
    setup = json.load(f)

url = f"https://www.example.com/pdf-api?id=&#123;id&#125;"
resp = requests.get(url, auth=HTTPBasicAuth(setup['token'], 'x'))

pattern = re.compile(r"filename\*?=[f']?(.*?)[']?(?:;?$)")
content_disp = resp.headers['Content-Disposition']
filename = pattern.search(content_disp).group(1)

with open(filename, 'wb') as f:
    f.write(resp.content)

这是一个完美的小脚本。每个代码块做一件事，每块只有几行，没有不必要的结构或样板代码——我喜欢。

## 4. Rye版本

由于这是Rye语言的博客，我们也会用Rye写这个 :)

rye .Args? .load .first :id
Load %setup.rye | context :setup
re : regexp "filename\*?=[f']?(.*?)[']?(?:;?$)"
format id https ://www.example.com/pdf-api?id=%d
| Request 'GET "" | Basic-auth! setup/token "x" | Call :resp
| Header? "Content-Disposition" | Submatch?* re | file.Create | Copy* Reader resp

有点不同，但类似。

## 5. 我们在假设什么？

脚本总是得到一个整数参数
setup文件存在且内容正确
HTTP请求从不失败
Content-Disposition头总是存在并包含文件名
我们总能创建新文件

正如Eugene Lewis Fordsworthe所说——这有很多假设 :(

## 6. 添加基本验证（第2步）

我可以像Eugene的稀释版本：用户输入是许多问题的根源。没有用户输入，就没有问题——但我们需要用户。所以让我们验证这些输入。

Python版本：
我们现在将：检查参数数量，检查ID是否为整数，检查setup是否有token值定义。

import sys, json, requests, re
from requests.auth import HTTPBasicAuth

if len(sys.argv) != 2:
    raise ValueError("script argument id - expected exactly one integer")

try:
    id = int(sys.argv[1])
except ValueError:
    raise ValueError("script argument id - must be an integer")

with open('setup.json') as f:
    setup = json.load(f)

if 'token' not in setup or not isinstance(setup['token'], str):
    raise ValueError("loading setup - token field required as string")

url = f"https://www.example.com/pdf-api?id=&#123;id&#125;"
resp = requests.get(url, auth=HTTPBasicAuth(setup['token'], 'x'))

pattern = re.compile(r"filename\*?=[f']?(.*?)[']?(?:;?$)")
content_disp = resp.headers['Content-Disposition']
filename = pattern.search(content_disp).group(1)

with open(filename, 'wb') as f:
    f.write(resp.content)

我们添加了这些检查，如果你问我（我有点偏见），优雅、可读的脚本已经消失了。这是我讨厌try/catch方法的原因之一。它增加了破坏代码流程的结构。

Rye版本：

rye .Args? .validate &#123; one integer &#125; | check "script argument id" | first :id
Load %setup.rye | context | validate &#123; token : required string &#125; | check "setup file" :setup
re : regexp "filename\*?=[f']?(.*?)[']?(?:;?$)"
format id https ://www.example.com/pdf-api?id=%d
| Request 'GET "" | Basic-auth! setup/token "x" | Call :resp
| Header? "Content-Disposition" | Submatch?* re | file.Create .defer \ 'Close | Copy* resp.Reader .defer \ 'Close

我们为参数和配置使用了验证方言（validation dialect）。并使用.defer\ 'Close确保资源（文件写入器和HTTP流读取器——顺便说一句，不复制到内存）被清理。脚本变得稍微复杂，但结构和流程没有改变。

## 7. 完整错误处理（第3步）

现在让我们处理所有失败情况，并在失败时向用户提供有用的反馈。我们最初优雅的脚本爆炸成了这样 :o

Python版本：
我们现在还检查：setup.json是否存在，能否解析setup.json的JSON，HTTP请求是否成功，如果没有Content-Disposition则提供默认文件名，能否创建新文件，能否将PDF写入其中。

import sys, json, requests, re
from requests.auth import HTTPBasicAuth

# Validate arguments
if len(sys.argv) != 2:
    print("Error: script argument id - expected exactly one integer")
    sys.exit(1)

try:
    id = int(sys.argv[1])
except ValueError:
    print("Error: script argument id - must be an integer")
    sys.exit(1)

# Load and validate config
try:
    with open('setup.json') as f:
        setup = json.load(f)
except (FileNotFoundError, json.JSONDecodeError) as e:
    print(f"Error: couldn't open config - &#123;e&#125;")
    sys.exit(1)

if 'token' not in setup or not isinstance(setup['token'], str):
    print("Error: loading setup - token field required as string")
    sys.exit(1)

pattern = re.compile(r"filename\*?=[f']?(.*?)[']?(?:;?$)")
url = f"https://www.example.com/pdf-api?id=&#123;id&#125;"

try:
    resp = requests.get(url, auth=HTTPBasicAuth(setup['token'], 'x'))
    resp.raise_for_status()
except requests.RequestException as e:
    print(f"Error: Http request failed - &#123;e&#125;")
    sys.exit(1)

# Extract filename with default fallback
content_disp = resp.headers.get('Content-Disposition', '')
match = pattern.search(content_disp) if content_disp else None
filename = match.group(1) if match else "default.pdf"

try:
    with open(filename, 'wb') as f:
        f.write(resp.content)
except IOError as e:
    print(f"Error: couldn't create local pdf - &#123;e&#125;")
    sys.exit(1)
except Exception as e:
    print(f"Error: couldn't save contents - &#123;e&#125;")
    sys.exit(1)

最初15行的脚本现在变成了45行代码，包含大量结构。工作代码隐藏在所有的安全代码中，几乎找不到。Python程序员自然会用一些辅助函数重构这个，使用像argparse和验证库这样的额外库，但这仍然给之前清晰的顺利路径增加了结构。它隐藏得更好，但也增加了依赖。

Rye版本：
我们给Rye版本添加了所有相同的检查。

rye .Args? .validate &#123; one integer &#125; | ^ check "script argument id" | first :id
Load %setup.rye | check "couldn't open setup file" | context | validate &#123; token : required string &#125; | ^ check "loading setup" :setup
re : regexp "filename\*?=[f']?(.*?)[']?(?:;?$)"
format id https ://www.example.com/pdf-api?id=%d
| Request 'GET "" | Basic-auth! setup/token "x" | Call | ^ check "Http request failed" :resp
| Header? "Content-Disposition" | Submatch?* re | fix &#123; "default.pdf" &#125; | file.Create | ^ check "couldn't create local pdf" | defer \ 'Close | Copy* resp.Reader .defer \ 'Close | ^ check "couldn't save contents"

代码变得更紧凑，但行数几乎没有增加，最重要的是，程序结构保持不变！:O

## 8. 但这是魔法吗？

上面的代码中没有魔法。你看到的所有单词都是常规的Rye函数。上面的代码只是Rye的前身、我们和一些运气做出的许多精心设计决策的结果。事实上，我们只使用了Rye失败和验证处理能力的一小部分。如果不先阅读更多关于Rye的内容，很难直接跳入，但上面的关键函数做了以下事情：

check - 返回值，如果不是失败；否则将失败包装在更高级别的失败中并返回
fix - 同样返回值，如果不是失败；否则评估一个块并返回该块的结果

我们上面使用的是相关函数。Rye有返回函数（returning functions）的概念（在Rye中，return也是一个返回函数——每个活动词（active word）在Rye中都是一个函数）。返回函数的命名约定是添加前缀^。^check - 类似于check，但在失败时也会返回/退出到调用者（更高级别的失败）。

这就是我不喜欢try/catch模型的原因之一，它是许多语言中主要的失败处理模型，当然不仅仅是Python。有更好的选择，我们在上面演示了一个，但这只是Go所做的一个改进版本，使用类型系统（Type system）和Option类型是另一种方法。这些方法有什么共同点？失败是语言中的一个正常值，应该与语言的功能融合，成为它的一部分。我打算写更多关于这个的内容。
