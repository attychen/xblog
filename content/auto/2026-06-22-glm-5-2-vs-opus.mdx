## 1. 概述：一场硬碰硬的较量

GLM-5.2 刚刚发布，这是开源模型能力的又一次进步。互联网迅速炸开了锅，但很难分辨哪些是真实的，哪些是炒作。因此，我们让它与 Claude Opus 4.8 进行了一场正面交锋：使用相同的单次提示（one-shot prompt），从零开始用原生 WebGL 构建一个 3D 平台游戏。以下是我们运行测试、深入研究基准测试和网络热议后的看法。我们不会将主力模型从 Opus 切换过来。在我们的测试中，Opus 速度更快，交付了一个更干净、更正确的游戏，并且它能够检查自己的视觉输出，而纯文本的 GLM-5.2 做不到这一点。但 GLM-5.2 在我们的武器库中赢得了一个永久席位：它是一款真正有能力的模型，价格却只有一小部分，而且由于它是开放权重（open weights），它将始终可用。一个闭源模型可能会在几乎没有预警的情况下被退役或限制使用（Fable 最近就是一个提醒）；而你可以下载的权重是无法被夺走的。你现在就可以试玩这两个游戏，或者获取源代码：GLM-5.2 的游戏：3dgame-glm.d.ritzademo.com；Opus 的游戏：3dgame-opus.d.ritzademo.com；两者的源代码：github.com/jamesdanielwhitford/glm-5.2-vs-opus-platformers。这是 GLM-5.2 从头到尾制作的内容。这是 Opus 从头到尾制作的内容。两者都是从头编写的浏览器游戏，没有使用游戏引擎或像 Three.js 这样的 3D 渲染库。3D 模型是来自 Kenney 的免费 CC0 资源。以下是两次运行的对比：指标 GLM-5.2 (Pi/OpenRouter) Opus (Claude Code)；挂钟构建时间 1小时10分40秒 33分30秒；输出令牌 131,000 216,809；峰值上下文窗口 1M的16% 1M的19%；工具调用 128 153；成本 $5.39（实际计费） ~$21.92（估算，标价）。GLM-5.2 的成本只有一小部分。Opus 在一半的时间内完成，并交付了一个更干净的游戏。从纸面上看，基准测试将 GLM-5.2 置于顶级闭源模型之后，而网络热议则是真实信号和人为炒作的混合体。我们将在游戏之后，在下面深入探讨这两点。

## 2. 什么是 GLM-5.2？定价与访问

GLM-5.2 是 Z.ai 最新的旗舰模型。它采用 MIT 许可证下的开放权重，因此你可以下载它，自己运行，或通过 Z.ai 的 API 调用它。它专为长周期任务（long-horizon tasks）而构建，即那种持续数小时的、多步骤的编码代理工作。它配备了 100 万令牌的上下文窗口和两个思考努力级别：高（High）和最大（Max），它们在速度和能力之间进行权衡。注意：GLM-5.2 是纯文本模型，不是多模态模型。它无法读取图像，因此围绕截图或图表的工作流程仍然需要像 Claude Opus 这样的模型。Z.ai 将其定位大致介于 Claude Opus 4.7 和 4.8 之间，使用相似的令牌数量。如果你想了解更多，这里是他们的公告：@Zai_org on X。由于它是开放权重的，GLM-5.2 很便宜。通过 API，它的成本只是 Opus 的一小部分，如果你有硬件，你可以免费自己运行。定价，每百万令牌（供应商文档）：输入 缓存读取 输出；Claude Opus 4.8 $5 $0.50 $25；GLM-5.2 $1.4 $0.26 $4.4。在输出令牌上，GLM-5.2 的价格不到 Opus 的五分之一。权重在 Hugging Face 和 ModelScope 上以 MIT 许可证提供，没有区域限制。你可以使用 vLLM、SGLang 或 Transformers 等框架在本地提供服务。

## 3. 我们的氛围测试：从零开始的 3D 游戏

为了排除干扰，我们给 Opus 4.8 和 GLM-5.2 相同的单次提示：从零开始，使用原生 WebGL，构建一个 3D 平台游戏，不使用游戏引擎或 3D 库。为什么选择这个任务？一个模型可以零样本生成一个好看的登录页面，社区已经不认为这是多大的考验了。一个原生 WebGL 的 3D 平台游戏无法用一个漂亮的文件来伪造。它有真实的结构：一个 GLB 模型解析器、矩阵和向量数学、GLSL 着色器、蒙皮骨骼动画、固定时间步长循环、碰撞、跟随摄像机。这种结构同时测试了人们争论的两件事。将分层的、多文件的构建过程在多个步骤中保持在一起，是代理部分，这也是 GLM-5.2 的强项。正确实现引擎内部逻辑，那些看起来没问题但会悄悄出问题的部分，是推理和品味部分，这也是 Opus 预计会领先的地方。我们将 3D 资源打包在本地，因此测试的是引擎和渲染，而不是工具是否能获取模型文件。美术资源本身是人工制作的资源包，Kenney 的 CC0 平台游戏套件，两个代理都获得了相同的文件。每个模型必须构建的内容：为了完成，每个模型必须构建：一个原生 WebGL 的 3D 引擎和渲染器，没有 Three.js 或任何库。一个用于加载提供的 3D 角色和世界模型的加载器。一个在竞技场上奔跑和跳跃的角色，具有重力和碰撞。一个跟随摄像机和键盘控制。整个东西可以在浏览器中用一条命令运行。两者大部分都是手工完成的（通过工具？通过爪子？）：一个 GLB 二进制解析器、矩阵和四元数数学、一个带有 GLSL 蒙皮着色器的 WebGL2 渲染器，以及子步进 AABB 碰撞，以防止角色穿透平台。两者都得到了相同的提示、相同的资源，并且只有一次尝试机会，没有提示。我们将 Opus 4.8 的扩展思考设置为高，GLM-5.2 的思考设置为高（GLM-5.2 还有一个更高的最大层级，我们没有使用）。你可以自己深入研究这两次运行：玩 GLM-5.2 的游戏：3dgame-glm.d.ritzademo.com；玩 Opus 的游戏：3dgame-opus.d.ritzademo.com；两者的源代码：github.com/jamesdanielwhitford/glm-5.2-vs-opus-platformers；Opus 构建记录：完整会话；GLM-5.2 构建记录：完整会话。花费了多长时间，成本是多少？Opus 4.8 在 Claude Code 中构建；GLM-5.2 在 Pi 上通过 OpenRouter 构建。并排延时摄影。Opus 在 34:00 完成，GLM-5.2 在 1:11 完成。延时摄影显示了整个构建过程的压缩：Opus 大约用了一半的挂钟时间完成工作，GLM-5.2 耗时更长，但花费的钱少得多。完整数字见顶部的结果表。

## 4. 游戏试玩与自我检查

我们从头到尾玩了这两个游戏。以下是每个游戏的表现。GLM-5.2，从头到尾。Opus，从头到尾。两者都构建了同类型的游戏：一个第三人称 3D 平台游戏，具有相同的控制方式。你可以用 WASD 或方向键移动，用空格键跳跃，用 Shift 键冲刺，通过拖动鼠标旋转摄像机，用滚轮缩放。目标也相同：收集平台上的硬币并到达旗帜，避开尖刺危险，从世界掉落会将你送回起点。GLM-5.2：GLM-5.2 的游戏看起来有点粗糙。从试玩来看：整体看起来不太好。角色缺少一些材质。尖刺危险不会杀死角色。到达旗帜没有任何反应。没有获胜条件。所以它并不太好。不过，它确实做好了一件事：弹簧。GLM-5.2 弹簧发射。你可以跳到弹簧上，弹射到下一个平台。Opus：Opus 的游戏更干净，玩起来也不错。从试玩来看：摄像机和控制器工作正常。尖刺危险会杀死玩家，所以逻辑是正确的。但它位于关卡的一侧，不在路径上，所以你必须特意去撞它。整体看起来不错，你可以到达旗帜并获胜。有真正的获胜条件。动画看起来不错，运行流畅，纹理应用正确。Opus：动画、纹理、控制器正常工作。每个模型如何检查自己的工作？两个模型都被要求在停止前验证自己的工作。代理这样做的一种常见方式是截取最终产品的屏幕截图并查看它，以检查是否有任何损坏或缺失。这正是 Opus 在其会话中所做的。GLM-5.2 在这里遇到了问题，因为它无法读取图像。它不是多模态的。因此，它没有查看屏幕截图，而是采用了一种粗糙的变通方法：它编写脚本来读取原始像素数据，并检查颜色是否大致符合预期。为什么 GLM-5.2 的自我检查错过了错误？因为它无法看到它保存的屏幕截图，GLM-5.2 试图通过读取像素来验证帧。以下是其最终报告的一段摘录，它通过采样颜色分析了保存的图像：final_start/overview/flag.png 分析颜色：草绿、土棕、金币金、旗帜红、角色蓝、半兰伯特光照、无黑色。它预期的颜色都在那里，因此它确认游戏已完成并停止。但是，从它自己的最终屏幕截图（如下）可以看出，角色是平坦的灰色，纹理丢失，调试覆盖层仍然覆盖在场景上。一个能够实际查看屏幕截图的代理很可能会发现这两个问题，并回去修复它们。GLM-5.2 的最终屏幕截图：角色纹理丢失，调试覆盖层仍在。它从未看到过这个帧。在一个有视觉结果的任务上，能够理解图像给了模型一个真正的优势，超过了不能理解图像的模型。Opus 如何检查自己的工作？Opus 是多模态的，因此它可以直接读取屏幕截图。它的工具渲染了游戏并捕获了一帧，Opus 检查了该图像作为其验证的一部分。以下是其会话的一段摘录，描述它看到了什么：最终场景渲染正确：草顶土边的方块、向上延伸的楼梯、金/银币和一颗宝石、右侧岛屿上的蓝色尖刺方块危险、顶部目标处的红旗、角色……站在起点广场上，以及分数 HUD。光照和着色正确，几何体干净。Opus 的屏幕截图：干净的 HUD，调试读数已移除。因为它能看到帧，Opus 注意到它留在屏幕上的调试读数，并在完成前清除了它们。

## 5. 错误分析

两个游戏都有错误。以下是每个游戏中出现的问题。GLM-5.2：GLM-5.2 的错误频繁且明显，其中几个是基础性问题。角色面朝错误的方向。它朝正确的方向行走，但模型全程是背对着的。纹理丢失和头部消失。角色渲染成平坦的灰色而不是有纹理的，并且每当摄像机移动时，它的头部就会消失。Kenney 模型指向一个单独文件中的共享调色板，而不是嵌入它，而 GLM-5.2 的渲染器从未加载该文件，因此它回退到纯色。Opus 加载了调色板，因此它的角色是有纹理的。死亡尖刺不会杀死角色。角色正好落在尖刺危险上，但什么也没发生。没有死亡，没有重置。Opus：Opus 的错误更少且更微妙，是边缘情况而不是基础功能损坏。站在半空中。角色可以坐在平台旁边，在半空中，而不会掉落。这是它的缓冲时间（coyote-time）宽限期，即你刚离开边缘后仍可以跳跃的短暂窗口，但调整得有点过于慷慨了。一个过度调整的优化功能，而不是一个损坏的基础功能。从太远的地方获胜。当角色距离旗帜还很远时，获胜条件就被触发了。测试表明了什么？两个模型都从零开始，在一次通过中构建了一个完整的、可运行的 3D 平台游戏，没有使用引擎和 3D 库。这是一个很高的标准，不久之前，两者都无法达到。以下是它们的差异。GLM-5.2：更慢、更粗糙、更便宜。GLM-5.2 花费了两倍多的时间，交付了一个粗糙的游戏：一个灰色的无纹理角色、一个不会杀人的尖刺、没有有效的获胜条件，以及最后屏幕上仍然存在的调试覆盖层。它的大部分错误都是基础性的。它的成本只有五分之一。Opus：更快、更干净、更昂贵。Opus 在一半的时间内完成，交付了更干净、更正确的游戏。它的错误是边缘情况，而不是基础功能损坏。它的成本大约是四倍。多模态优势：Opus 可以读取图像，因此它的自我检查查看了渲染的游戏并发现了视觉问题。GLM-5.2 是纯文本的：它通过数字进行验证，从未看到它的角色是灰色的，或者它的调试覆盖层仍然存在。在一个视觉任务上，这就是发现粗糙边缘和交付它们之间的区别。一个游戏只是一个数据点。下面的基准测试在更大规模上测试了相同类型的能力。

## 8. 结论

那么，炒作是真的吗？大部分是。GLM-5.2 是一个真正强大的开放模型，价格只有 Opus 的一小部分。对于很多工作来说，这种组合很难被击败。但它不是 Opus。在我们的测试中，Opus 更快，交付了一个更干净、更正确的游戏，并且可以通过查看自己的作品来检查自己的工作。GLM-5.2 便宜得多，但更粗糙，而且是纯文本的。当成本和开放性很重要，并且工作主要是文本和逻辑时，使用 GLM-5.2。当正确性、精致度和视觉判断很重要时，使用 Opus，并且你会为此付费。无论如何，将 GLM-5.2 保留在武器库中：它是罕见的接近前沿的模型，没有供应商能将其从你手中夺走。
