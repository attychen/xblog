## 1. 引言

本规范定义了HTTP QUERY请求方法，作为一种进行安全、幂等请求（[HTTP]第9.2节）的手段，该方法包含一个描述目标资源如何处理请求的表示。

常见的查询模式是：

GET /feed?q=foo limit=10 sort=-published HTTP/1.1
Host: example.org

然而，当传输的数据量过大而无法编码到请求的URI中时，这种模式就会变得有问题：

- 大小限制通常无法提前知晓，因为请求可能经过许多不协调的系统（但请注意，[HTTP]第4.1节建议发送方和接收方至少支持8000个八位字节）。
- 在目标URI中表达某些类型的数据效率低下，因为将数据编码为有效URI的开销较大。
- 请求URI比请求内容更可能被记录，也可能出现在书签中。
- 将查询直接编码到请求URI中，实际上会将查询输入的每一种可能组合都视为不同的资源。

作为使用GET的替代方案，许多实现使用HTTP POST方法来执行查询，如下例所示。在这种情况下，查询操作的输入作为请求内容传递，而不是使用请求URI的查询组件。

使用HTTP POST请求查询的典型用法是：

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo limit=10 sort=-published

然而，在这种变体中，如果不具体了解所请求的资源和服务器的知识，就不容易看出正在执行的是安全、幂等的查询。

QUERY方法提供了一种弥合GET和POST之间差距的解决方案，上面的例子可以表示为：

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo limit=10 sort=-published

与POST一样，查询操作的输入作为请求的内容传递，而不是作为请求URI的一部分。然而，与POST不同的是，该方法明确是安全且幂等的，允许缓存和自动重试等功能正常运行。

认识到任何重要资源都应通过URI来标识的设计原则，本规范描述了服务器如何为查询本身或特定的查询结果分配URI，以便后续在GET请求中使用。

总结如下：

表1：相关方法属性总结

| 属性 | GET | QUERY | POST |
| --- | --- | --- | --- |
| 安全 | 是 | 是 | 可能否 |
| 幂等 | 是 | 是 | 可能否 |
| 查询本身的URI | 是（按定义） | 可选（Location响应字段） | 否 |
| 查询结果的URI | 可选（Content-Location响应字段） | 可选（Content-Location响应字段） | 可选（Content-Location响应字段） |
| 可缓存 | 是 | 是 | 是，但仅适用于未来的GET或HEAD请求 |
| 内容（主体） | 无定义语义 | 期望（语义按目标资源） | 期望（语义按目标资源） |

1.1. 术语

本文档使用[HTTP]第3节中定义的术语。

此外，它使用术语URI查询参数（URI query parameter）指代URI查询组件中的参数（[HTTP]第4.2.2节），并使用术语查询内容（query content）指代QUERY请求的请求内容（[HTTP]第6.4节）。

1.2. 符号约定

本文档中的关键词“必须（MUST）”、“禁止（MUST NOT）”、“必需（REQUIRED）”、“应当（SHALL）”、“应当不（SHALL NOT）”、“应该（SHOULD）”、“不应该（SHOULD NOT）”、“推荐（RECOMMENDED）”、“不推荐（NOT RECOMMENDED）”、“可以（MAY）”和“可选（OPTIONAL）”应按照BCP 14 [RFC2119] [RFC8174]中的描述进行解释，且仅当它们以全大写形式出现时。

## 2. QUERY方法

QUERY方法用于发起服务器端查询。与GET方法（请求目标URI所标识资源的表示，如[HTTP]第7.1节所定义）不同，QUERY方法用于请求目标资源在该目标资源的范围内执行查询操作。

请求的内容及其媒体类型定义了查询。源服务器根据目标资源确定操作的范围。

如果Content-Type请求字段（[HTTP]第8.3节）缺失或与请求内容不一致，服务器必须（MUST）拒绝该请求。

对于所有HTTP方法，目标URI的查询部分参与标识被查询的资源。它是否以及如何直接影响查询结果，是资源特定的，并且超出了本规范的范围。

QUERY请求相对于目标资源是安全的（[HTTP]第9.2.1节）；也就是说，客户端不请求也不期望目标资源的状态发生任何变化。这并不阻止服务器创建额外的HTTP资源，通过这些资源可以检索附加信息（参见第2.3节和第2.4节）。

此外，QUERY请求是幂等的（[HTTP]第9.2.2节）；它们可以在需要时重试或重复，例如在连接失败后。

根据[HTTP]第15.3节，2xx（成功）状态码表示请求已成功接收、理解并被接受。

特别地，200（OK）响应表示查询已成功处理，并且处理结果作为响应内容包含在内。

2.1. 媒体类型与内容协商

QUERY请求的语义取决于请求内容以及相关的元数据，例如媒体类型（[HTTP]第8.3.1节）。通常，任何内容与元数据不一致的请求问题必须（MUST）以4xx（客户端错误）响应拒绝（[HTTP]第15.5节）。

下面列出了各种失败情况，并推荐了特定的状态码：

- 如果请求缺少媒体类型信息，则按定义是不正确的，需要以4xx状态码（如400（客户端错误））失败。
- 如果指定了媒体类型但资源不支持，则适合使用415（不支持的媒体类型）。这特别包括媒体类型原则上已知，但缺乏针对目标资源QUERY的特定语义的情况。在这两种情况下，可以使用Accept-Query响应字段（第3节）通知客户端支持的媒体类型。
- 如果指定了媒体类型但与实际请求内容不一致，可以返回400（错误请求）。也就是说，不允许服务器从请求内容推断媒体类型，然后覆盖缺失或错误的值（即内容嗅探）。
- 如果媒体类型被指定且理解，内容确实与类型一致，但由于查询的实际内容而无法处理查询，则可以使用状态码422（不可处理的内容）。例如，语法正确的SQL查询标识了一个不存在的表。
- 如果客户端使用Accept字段（[HTTP]第12.5.1节）请求了资源不支持的特定响应媒体类型，则适合使用状态码406（不可接受）。

2.2. 等价资源

任何给定QUERY请求的等价资源（equivalent resource）是一个响应GET请求的资源，它代表该QUERY请求及其目标，并考虑消息内容和元数据（[HTTP]第6节）。特别地，这包括表示元数据（[HTTP]第8节），例如内容的媒体类型。

换句话说，等价资源是通过合并请求内容从实现QUERY的资源派生出来的。

术语“等价资源”被用作定义其他HTTP方面行为的手段，例如选定的表示（selected representations）。服务器可以但不必须为这些资源分配URI（参见[URI]第1.1节）。如果它们这样做，这些资源将变得可通过GET请求访问。

2.3. Content-Location响应字段

成功的响应（2xx，[HTTP]第15.3节）可以包含一个Content-Location头字段，其中包含对应于操作结果的资源的标识符；详细信息请参见[HTTP]第8.7节。这表示服务器声称客户端可以向指示的URI发送GET请求，以检索刚刚执行的查询操作的结果。指示的资源可能是临时的。

示例请参见附录A.4.1。

2.4. Location响应字段

服务器可以为QUERY请求的等价资源（第2.2节）分配一个URI。如果服务器这样做，该资源的URI可以包含在2xx响应的Location头字段中（参见[HTTP]第10.2.2节）。这表示服务器声称客户端可以向指示的URI发送GET请求，以重复刚刚执行的查询操作，而无需重新发送查询内容。此资源的URI可能是临时的；如果未来的请求失败，客户端可以使用原始的QUERY请求目标和先前提交的内容重试。

示例请参见附录A.4.2。

2.5. 重定向

在某些情况下，服务器可能选择通过将用户代理重定向到不同的URI来间接响应QUERY请求（参见[HTTP]第15.4节）。

状态码为301（永久移动，[HTTP]第15.4.2节）或308（永久重定向，[HTTP]第15.4.9节）的响应表示目标资源已永久移动到由Location响应字段（[HTTP]第10.2.2节）引用的不同URI。同样，状态码为302（找到，[HTTP]第15.4.3节）或307（临时重定向，[HTTP]第15.4.8节）的响应表示目标资源已临时移动。在这四种情况下，服务器建议用户代理可以通过向Location引用的新目标URI发送类似的QUERY请求来完成其原始的QUERY请求。

请注意，在301或302响应后将POST重定向为GET请求的例外情况不适用于QUERY请求。

状态码为303（参见其他，[HTTP]第15.4.4节）的对QUERY的响应表示可以通过对Location响应字段（[HTTP]第10.2.2节）引用的URI进行正常的检索请求来完成原始查询。对于HTTP，这意味着向新的目标URI发送GET请求，如附录A.4.3中的示例所示。

2.6. 条件请求

QUERY请求的选定表示（[HTTP]第3.2节）与对该QUERY请求的等价资源（第2.2节）进行GET请求的选定表示相同。

条件QUERY请求仅在条件头字段描述的情况下（如[HTTP]第13节所定义），才在响应中返回选定的表示（即内容协商后的查询结果）。

示例请参见附录A.5。

2.7. 缓存

对QUERY方法的响应是可缓存的；缓存可以（MAY）使用它来满足后续的QUERY请求，如[HTTP-CACHING]第4节所述。

QUERY请求的缓存键（[HTTP-CACHING]第2节）必须（MUST）包含请求内容（[HTTP-CACHING]第6节）和相关元数据（[HTTP]第8节）。

为了提高缓存效率，缓存可以（MAY）首先从请求内容和相关元数据中移除语义上不重要的差异。例如，通过：

- 移除内容编码（[HTTP]第8.4节）。
- 基于对格式约定的知识进行规范化，如请求的Content-Type字段中的任何媒体子类型后缀所示（例如，+json；参见[RFC6838]第4.2.8节）。
- 基于对内容本身语义的知识进行规范化，如请求的Content-Type字段所示。

请注意，任何此类转换仅用于生成缓存键；它不会改变请求本身。

客户端可以使用no-transform缓存指令（[HTTP-CACHING]第5.2.1.6节）表示不希望发生此类转换（但请注意，此指令仅为建议性）。

请注意，缓存QUERY方法的响应本质上比缓存对GET的响应更复杂，因为需要完整读取请求内容才能确定缓存键。如果QUERY响应提供了Location响应字段（第2.4节）来指示等价资源（第2.2节）的URI，客户端可以在后续请求中切换到GET，从而简化处理。

2.8. 范围请求

QUERY的范围请求语义与GET相同，如[HTTP]第14节所定义。然而，字节范围请求（撰写本文时定义的唯一范围单位）对于QUERY请求的结果提供的价值很小。

查询格式通常定义自己的限制或分页结果集的方式，例如SQL中的FETCH FIRST ... ROWS ONLY。预计这些内置功能将被使用，而不是HTTP范围请求。

## 3. Accept-Query头字段

资源可以使用Accept-Query响应头字段直接表示对QUERY方法的支持，同时标识可能使用的特定查询格式媒体类型。

Accept-Query包含一个媒体范围列表（[HTTP]第12.5.1节），使用结构化字段语法[STRUCTURED-FIELDS]。媒体范围由Token或String类型的列表结构化头字段表示，包含不带参数的媒体范围值。

媒体类型参数（如果有）映射到具有String或Token类型的结构化字段参数。Token与String的选择在语义上不重要。也就是说，接收者可以（MAY）将Token转换为String，但不得（MUST NOT）根据接收到的类型进行不同的处理。

媒体类型不能精确映射到Token；例如，它们允许前导数字。在这种情况下，需要使用String格式。

唯一支持的通配符用法是*/*（匹配任何类型）或xxxx/*（匹配指定类型的任何子类型）。

字段值中列出的类型顺序不重要。

Accept-Query字段的值适用于服务器上共享相同路径的每个URI；换句话说，查询组件被忽略。如果对同一资源的请求返回不同的Accept-Query值，则使用最近接收到的有效值（根据[HTTP-CACHING]第4.2节）。

例如：

Accept-Query: application/jsonpath, application/sql;charset=UTF-8

尽管此字段的语法看起来与其他字段（如Accept（[HTTP]第12.5.1节））相似，但它是一个结构化字段，因此必须（MUST）按照[STRUCTURED-FIELDS]第4节的规定进行处理。

## 4. 安全考虑

QUERY方法受到与[HTTP]中描述的所有HTTP方法相同的一般安全考虑。

它可以作为在URI中传递请求信息（例如，在查询组件中）的替代方案。在某些情况下，这是首选，因为URI比请求内容更可能被中介记录或以其他方式处理。在其他情况下，当查询包含敏感信息时，URI被记录的可能性可能会促使使用QUERY而不是GET。

如果服务器创建一个临时资源来表示QUERY请求的结果（例如，用于Location或Content-Location字段），为该资源分配一个URI，并且请求包含无法记录的敏感信息，那么该URI应该（SHOULD）被选择为不包含原始请求内容的任何敏感部分。

如果缓存不正确或与资源处理内容的方式显著不同地规范化QUERY内容，并且规范化导致误报，则可能返回不正确的响应。

来自实现跨源资源共享（CORS）的用户代理的QUERY请求将需要预检请求，因为QUERY不属于CORS安全列表方法集（参见[FETCH]）。
